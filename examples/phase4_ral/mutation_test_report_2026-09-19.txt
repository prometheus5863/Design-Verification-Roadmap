1. THE HARNESS HAD THE BUG IT EXISTS TO CATCH. The first run of this
   script reported 0 killed / 5 survived. Every one of the five logs
   contained the correct FAIL. The script was trusting `make`'s exit
   status, and with cocotb 1.9.2 + Icarus 10.3 `make` exits 0 even when
   cocotb prints TESTS=1 PASS=0 FAIL=1. Verified directly:

       $ make RTL_SRC=.../uart_controller_M3.v >/dev/null 2>&1; echo $?
       0

   This is the third appearance of one defect class in this repo
   (2026-09-17: checks never ran; 2026-09-18: cocotb PASS line ignored
   UVM_ERRORs; today: make's exit code ignored cocotb's FAIL). Each time
   the verdict came from a different subsystem than the checking. The
   script now parses cocotb's own results line and distinguishes
   NORESULT (crash/compile error) from a kill, because a crash is not
   evidence that a check works.

   ACTION FOR A FUTURE SESSION: examples/phase4_uvm_milestone has no
   mutation script, only a report; whoever automates it must not use
   make's exit code either.

2. M2 IS NOT A CLEAN SINGLE-TARGET MUTANT. Changing BAUD_DIV's reset
   value from 0 to 1 halves the baud rate, so the hand-driven bad frame
   in CHECK 5 is also sent at the wrong rate and frame_err never gets
   set. M2 is killed by UVMRegHWResetSeq as intended, but it is ALSO
   killed by CHECK 5 for an unrelated reason. That is collateral, not
   extra confidence: a mutant that trips two unrelated checks tells you
   less about either than one that trips exactly the check it targets.
   Recorded rather than presented as 'two checks caught it'.

3. WHAT 5/5 DOES NOT MEAN. It is a claim about five defects in the
   register interface, not about the DUT or about the RAL. Untouched by
   any mutant here: the baud generator, the TX/RX shift engines, the
   FIFO full/empty logic, the interrupt OR, the loopback mux, and
   RX_DATA's FIFO-pop-on-read -- which is precisely the behaviour no
   uvm_reg access policy can express, and so the one thing the register
   model structurally cannot check.
