SECTION 4.  F2  (none, parity) is POPULATION-unsound by construction
==============================================================================
  Mechanism, traced through the committed source:
    UartConfig.expected_parity() returns None when parity is
    disabled; UartSerialMonitor then skips the parity-bit sample
    entirely, so item.parity_ok keeps the True it is initialised
    with; UartCoverage.write_rx classifies on `not item.parity_ok`
    first, so the "parity" class is unreachable under PARITY_NONE.
    No stimulus closes (none, parity).  It is not scarce; it is
    EMPTY OF ADMISSIBLE WITNESSES.
  [PASS] F2a  the committed 100 % run never closes (none, parity)  -- cross cells closed: 8 of 9
  [PASS] F2b  and it is the ONLY cell the run misses, so the run is at the achievable ceiling rather than merely incomplete  -- missing = [('none', 'parity')]

  achievable cross cardinality : 8/9 = 88.89 %
  achieved                     : 8/9 = 88.89 %

  F1 AND F2 INTERACT, AND THAT IS WHY NEITHER IS FIXED HERE.
  Adding the cross to coverage_percent() in the obvious way -- fold
  its 9 cells in beside the 19 bins -- makes the metric top out at
  96.43 % against a TARGET of 100.0, so the gate becomes
  UNSATISFIABLE and every milestone run starts failing COV_TARGET.
  The remedy needs an exclusion (an illegal_bins equivalent) landed
  in the SAME change, and choosing it changes a committed sign-off
  criterion -- a reviewer's decision, per the standing treatment of
  F7's goal.  Recorded as an open item, not taken.

SECTION 6.  F4  The TEMPORAL axis, exhibited rather than asserted
==============================================================================
  2026-10-04 filed "is there a FOURTH soundness axis?" as a
  QUESTION and named temporal as the next candidate.  It is present
  here, and the window is structural rather than probabilistic:

    UartCoverage._parity_name() reads self.cfg.parity_mode
    UartConfigSeq.body()        writes CTRL to the DUT, THEN
                                assigns self.cfg.parity_mode

  Between those two statements the DUT is operating under the new
  parity mode and the shared cfg object still holds the old one, so
  any RX frame sampled in the window is filed in the cross under a
  parity mode that was not in force for it.  The frame is a
  perfectly ADMISSIBLE witness of its own rx_error class; what is
  wrong is the OTHER coordinate of the cross cell it closes.
  [PASS] F4a  UartConfigSeq.body located in the committed source  -- line 1363
  [PASS] F4b  the CTRL write to the DUT precedes the cfg update in program order, so the window is real and not an artefact of my reading  -- CTRL write at line 1367, cfg update at line 1368 -- window spans 1 statement line(s)

  THE AXIS IS NOT THE BUG.  The window here is narrow and the
  milestone sequence does not drive RX traffic across it, which is
  why no committed number is wrong and none is withdrawn.  The
  finding is that the FOURTH AXIS HAS A CONCRETE INSTANCE in the
  first collector it was pointed at, so it should stop being filed
  as a question.  A coverage sample has a TIMESTAMP, and a sample
  whose coordinates are read from two sources that are updated at
  different times is sound on each coordinate and unsound as a
  pair.  No cardinality, scarcity, population or run check sees it:
  all four ask about the SET of witnesses, and this is a question
  about WHEN one was read.
